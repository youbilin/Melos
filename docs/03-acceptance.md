## 0.1.9 转码流曲尾错误（根因）

- 现象：音质设为 320 kbps 转码时，每首播完报 `播放失败：decode error request or response body error`，下一首不播；与是否随机无关。
- 根因：`stream_url` 对转码请求附带 `estimateContentLength=true`。服务端声明的是估算长度，实际 MP3 转码更短，客户端读到估算末尾前连接结束，hyper 以“不完整响应体”报错，非转码流（raw）不受影响。
- 证据：同一服务、同一账号，三首转码流完整解码：修复前 **3/3** 以 `request or response body error` 结束（容器时长为 null，已解码 230,976 / 230,504 / 341,681 ms，与 API 时长一致）；去掉估算长度后 **3/3** 正常结束、零错误。raw FLAC 与 40 首随机样本此前均无错误，说明问题只在转码路径。
- 修复：转码地址不再发送 `estimateContentLength`，由分块编码给出真实结束；解码器支持用服务端时长兜底“已解码到末尾但读取失败”的判断。0.1.8 的 90%/1 秒容差保留为第二层保护。
- 回归：新增“服务端时长兜底无容器时长的尾部读取失败”，共 86 个测试通过；转码流 3/3 完整解码为本次真实服务检查。窗口内跨曲续播仍待用户复测后记录。

## 0.1.8 曲尾连接中断

- 真实服务反馈：一首播完后不继续，界面报 `播放失败：decode error request or response body error`。该文本是 reqwest 的响应体错误，经解码器外层包装成 `PlayerError::Decode`。
- 原因判断：本轮只读诊断对最新专辑的 8 首原始流做完整解码，全部正常结束；随后用引擎在真实服务上播放三首 FLAC，并从首曲末尾前 12 秒开始，两次跨曲边界均正常。因此问题集中在“服务器在最后一批音频后提前断开”这一尾部读取失败，而不是整条流不可用。
- 修复：尾部读取失败时，若已解码至少 90% 且与声明时长相差不超过 1 秒，视为正常结束并继续下一首；中途断开、明显截断和传输错误仍报错。失败读取可能丢掉最后一个编码帧组（约 60 ms），不构成停播。
- 回归：新增“完整文件后连接中断正常结束”和“中途断开仍报错”两个测试，共 85 个测试通过；引擎跨曲测试不是自动化回归，仍需在真实服务上复测同一首歌的跨曲行为。
